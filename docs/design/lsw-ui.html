The preview's three looks

LSW, Overview, preview

Open desktop

lsw desktop
Why it starts paused
The preview is the guest's primary monitor captured inside Windows (Windows Graphics Capture), sent the way the window mirrors send theirs, and drawn read-only: no pointer, wheel or key reaches the guest from it. A live capture costs the guest's GPU a copy of every frame and the host a draw of it, all for a thumbnail nobody may be watching. So the preview asks the agent for a capture, takes the first frame, and lets the capture go. The frame stays, desaturated and dimmed, with the pause badge over it and the tag ending in paused, so a still picture is never mistaken for a live one. A click plays it live, the tag saying how the frames come (wgc, gpu when they stay on the GPU, wgc, pixels when they do not); a second click pauses it again on the frame it was showing. Hidden, it captures nothing, and a preview that was playing plays again when it is shown. With no guest, the guest off, or its agent not answering yet, the screen is flat grey with no badge and the tag says which, because there is nothing to play. A capture that fails says why in the tag and goes back to the paused look; the badge then tries again.
Open desktop
The guest's whole screen in a window of its own, a real one: the window mirror captures the primary monitor inside Windows (Windows Graphics Capture) and draws it one guest pixel to one screen pixel, centred, when the window has room, and scaled down and letterboxed in black when it has not. The pointer and the keyboard go into the guest, and the guest's cursor is this window's own cursor rather than painted into the picture, so it follows the pointer with no lag. Its title is the machine's name and desktop, lsw desktop here. One window at a time: with it open, the button brings it to the front. Disabled, with nothing else on the bar changing, while the agent is offline: the capture runs inside Windows, so there is nothing to open until Windows answers. The preview above is the same capture, read-only and paused until clicked.
Why the rail
Four buttons in a row said nothing about where you were, and two of them were always disabled. The rail marks the current section, keeps the count of unread log records and pending settings in view, and leaves one power control instead of a Start and a Stop that take turns being dead.
One power button
It reads Stop the guest while running and Start the guest while off. The state badge above it is the thing that changes color, not the button.
Console and log
Now sections in the same window rather than separate top level windows. Pop out is still there for anyone who wants a second window.
Status bar
The transport facts that currently only exist in logs: the agent's port and the bus the disk sits on.
GPU line
The third line of the identity is the display adapter's host GPU, by its Vulkan device name, which is also the adapter's name inside Windows, and how many render-only adapters sit beside it. It is in the rail, so it is on every page; the Graphics page has the rest.
VRAM gauge
The host GPU's used and total VRAM, read on the host (mem_info_vram_used and mem_info_vram_total for amdgpu, NVML for NVIDIA), because what the guest allocates lives there. It counts everything on that GPU, the host desktop included. Windows' own dedicated memory figure is a budget the driver reports, not a place anything is put, so it is not a gauge. A host GPU that exposes neither hides the row.
Keeping Windows' half current
LSW's pieces inside Windows travel with LSW, so an LSW update brings new ones for every guest, including those set up by older releases. Each time the agent answers, once setup has finished, the manager compares the agent and the window mirror's guest half with the ones it ships and swaps any that differ, the agent restarting on the new binary; an agent too old to say what it is counts as different. While that runs, Updating LSW in Windows is a fact in the status bar. If it fails, the notice says why, with Try again; it is tried once per start of the manager otherwise, so a swap that keeps failing does not loop. The driver package is not part of this: it changes the display driver, so it waits for the user on the Graphics page.
Windows' clock
The VM's hardware clock runs on the host's local time, which Windows reads as its own: in another time zone, its clock is hours off after every boot. So the manager gives Windows the host's time zone, and the host's time when Windows' clock is more than two seconds off, each time the agent answers. Nothing is shown for it unless it fails, which is a notice like any other.
Notices
Something the manager tried that did not work is said once, in a strip across the top of the page, under the header: an application that could not be opened, libvirt refusing to start the guest or to take a new definition, the resolution not reaching the guest, the disk not growing, the desktop not opening. Red when the guest cannot run because of it, amber otherwise. The headline names what failed, the rest says why in the words that came back, and the buttons are what helps: Open the log, Open desktop, then Dismiss, quiet and last, on every one. They show on every page, newest first, one per kind of failure: the same failure again replaces its strip, and one that stops being true (the guest starts after all, the application opens on a second try) takes its strip away. Progress (Restarting the guest) is not a notice; it is a fact in the status bar while it lasts. Nothing pops up a message box.
Warning strip
Not shown here, because nothing is wrong. It appears on the overview for the Graphics warnings that break the guest: the host serves no Direct3D, or Windows is not running avgpu.sys (including having no driver for a display GPU switched since the install). It also appears for a driver update LSW brought, so it is not missed. Its button opens the Graphics page.
Manager

Graphics

The guest's graphics adapters are this machine's GPUs. accel-virt gives Windows one paravirtual device per host GPU passed to it, named after that GPU, with its IDs and its VRAM, and every Direct3D, Vulkan, OpenGL and OpenCL call crosses to the host and runs on the host's own drivers. One adapter is the display; any others are render only, with no outputs, and applications pick between them as they would between two cards. There is nothing to assign per application. This page says which GPUs those are, what the host can serve on them, and whether the guest's driver runs on each.

What it warns about

LSW, Graphics, warning strips
The host serves no Direct3D. DXVK and vkd3d-proton were not found, and Windows draws its desktop with Direct3D 11, so it will keep restarting until they are.
Windows is not running avgpu.sys. The adapter reports problem code 52: test signing is off, so Windows refused the driver's signature.
Windows has no driver for Intel UHD Graphics 770. It was added as an adapter after the driver package was installed, so Windows has not matched it to avgpu.sys yet.
A driver update is ready for the guest. LSW was updated with a different avgpu.sys package than Windows has: 9 of its 12 files changed.
Installing the driver for new adapters. Signing a fresh copy of the package for their IDs, then pnputil. About a minute. signing
The adapters
One card per host GPU passed to the guest, the display adapter first and each render-only one after it. Name, IDs, UUID, memory and driver come from the host's own Vulkan enumeration, the same data list_gpus.py reads: deviceName, vendorID and deviceID, deviceUUID, the device-local heap, driverName and driverInfo. Windows sees exactly these names and IDs in Device Manager, dxdiag and DXGI, so what this page says and what an application says agree. Which GPUs are passed, and which one is the display, is set in Settings, under Graphics.
State per adapter
The pill on each card is Windows' side of that adapter, from the agent: Started, No driver (problem code 28, an adapter Windows has no driver for), or Problem code N. The agent's adapters are matched to the cards by vendor and device ID, then by name.
Dedicated memory
The host GPU's VRAM, reported to Windows as dedicated video memory. It is a budget, not a place: nothing is ever put in that segment, and what applications allocate lives on the host GPU. That is why the card gives no "used" figure for it. An integrated GPU has no device-local heap of its own and reads shared.
API checks
Probed on the host, off the window's thread, when the manager starts, at every boot and on Check again, the way the executor decides: a Vulkan driver, EGL with desktop OpenGL, an OpenCL ICD, and DXVK's and vkd3d-proton's native libraries in the folder LSW passes as AV_D3D_PATH. One block for every adapter, because each one's executor makes the same checks; where the Vulkan drivers differ the row names each. An API the host lacks is not offered to the guest, and its row reads Not served in grey. Applications that need it fail as they would on a card without it.
Only what was found
"The host runs it on" is what the host probe found and nothing else: driver names from Vulkan, EGL and the OpenCL ICDs, and a DXVK or vkd3d-proton version only where the library's file name carries one. What Windows makes of each API is not shown: only the guest could say, and nothing asks it.
Direct3D is different
Windows composes its desktop with Direct3D 11. Without DXVK and vkd3d-proton on the host, DWM crash-loops with 0x889800B2. So these two rows go red with Missing, the rail gets a red dot, and the strip above shows on the overview too. Check again repeats the probe; it does not need a restart to clear the warning, but the guest needs one to get Direct3D.
Device
What the running domain's live definition has on its virtio-gpu-av-pci lines, read back from libvirt rather than from the settings: host-gpu, hostmem, and one display=off device per render-only GPU; with the machine off, the stored definition the next start boots. Fixed for the life of the machine; change them in Settings, under Graphics, and they land at the next restart, which the row says beside the value ("16 GiB after a restart") until then. "Taken by the driver" is the driver's own host window status line.
Display is live
Read from the display adapter's modes property and updated when it changes. The Switch resolution list in the card's header holds the modes offered; picking one makes it preferred, in Settings as well, and is a qom-set on that property: the device raises a display event, the driver replugs its monitor, and Windows switches. No restart. Vsync is a fixed 60 Hz.
Guest driver
From the agent, once per boot and after an install: every accel-virt adapter, found by its subsystem 1af4:5256 or the avgpu service, with its problem code and installed DriverVersion, one line each; TESTSIGNING in the boot options; and the driver search policy provisioning set. Windows Update would otherwise offer the vendor's real driver for these IDs, and on this device the real driver bugchecks. Submission comes from the driver log's user-mode submission and native fences lines.
New adapters
The driver package is signed for the PCI IDs present when Windows was installed, and the accel-virt adapter wears the PCI ID of the host GPU behind it, so a GPU passed later is an adapter Windows has no driver for. So is the display adapter once the machine's GPU is switched to another one: then it is the red strip, Windows has no driver for the new GPU, with the same install button and the driver log beside it, and the overview carries it too. Install the driver for new adapters runs, through the agent, a re-sign of a clean copy of the package (C:\av\pristine, kept by setup, mirrored to C:\av\resign) and provision.ps1 -Stage install. A clean copy, because signing rewrites the INF and signs avgpu.sys, which no longer match the package's own checksums. Progress shows in the strip; when the installer asks for one, the strip offers a restart, and the card reads Started after it.
Driver updates
The driver package ships with LSW (share/lsw/guest/av-drivers), so an LSW update can carry a new one. Its package.sha256, the checksum of every file, is compared with the one in the guest's C:\av\pristine\package, which the agent reports with the adapters. When they differ the amber strip A driver update is ready for the guest says how many files changed, and the overview carries it too. Update the driver uploads the package, provision.ps1 and the OpenCL loaders through the agent, puts them in C:\av and C:\av\pristine, and then runs the same re-sign and install as for new adapters, with the same progress and restart in the strip. A guest set up before setup kept a pristine copy reports none and is not offered the update.
Driver log
avgpu.sys writes avgpu: ... lines to I/O port 0x402. An isa-debugcon device on the machine puts them in avgpu.log in the data folder, across reboots and up to a bugcheck, so it still has the last line when Windows does not. The panel tails the file; the button opens all of it in the host's text editor.
What warns
Three things, each something the user can act on. No Direct3D on the host, red. The display adapter not running avgpu.sys, red: a problem code from the agent, usually a refused signature or a replaced driver; for problem code 28, a GPU switched since the install, the strip offers the install instead of only the log. A render-only adapter with no driver, amber, with the install button. A driver update LSW brought, amber, with the update button. The rail dot takes the worst color present. Nothing else on the page changes color.
Nothing per application
Every process opens the adapters through Windows' own loaders, so there is nothing to claim, pin, wait for or release. Applications pick a render-only GPU the way they pick between two physical cards.

Restart is explicit
Nothing reboots behind your back. Restart-only fields are tagged restart, edits stay staged, and the bar at the bottom shows exactly what changed before it offers the reboot.
Live fields apply on the spot
Tagged now, written to manager.toml as they change. Mixing the two kinds in one page is fine as long as each row says which it is.
Pending count
The rail shows an amber count next to Settings, so a staged change is visible from any other section.
Files
The SMB path already exists: the machine forwards 127.0.0.1:5445 to the guest's 445, and the bookmark is served in userspace by the file manager rather than mounted, so Windows junctions never turn into a pile of extra mounts. The new part is the GTK bookmark file beside the KDE one, the choice of what to share, and a host folder going the other way.
Desktop entries
Publishing already writes a .desktop and a menu fragment per application. The page adds the category name, a per-application choice, file type handlers, and a rewrite button for when a launcher is showing a stale icon.
Display
The host decides which modes the guest's display offers, and can change them while Windows runs. The list is the device's modes property, WxH between commas, the first preferred; LSW sets it with a qom-set, the device raises a display event, the driver replugs its monitor, and Windows switches when the list lacks the mode it is showing. So the list, the preferred mode and matching the monitor all apply now. An empty list is the host monitors' own modes. So does the scale: the agent sets it the way Windows' own Settings does, in the user's session, which only takes Windows' steps (100, 125, 150 %...), so a host scale between them goes to the nearest. The adapter's video memory is no longer a setting: it is the host GPU's VRAM.
Resolution limits
The editor refuses what the driver would silently drop, with the reason beside the field: an edge under 100 (the smallest source mode dxgkrnl accepts), an edge over 4095, or a pixel clock over 655.35 MHz. The driver times every mode at 60 Hz with 160 pixels of horizontal blanking and one blank line per 24 active ones, so the clock is (W + 160) × (H + H/24) × 60, which an EDID detailed timing stores in 10 kHz units up to 65535. 3840 × 2160 is 540 MHz and fits. The device carries at most 32 modes. Presets are the common sizes and the monitors connected to this machine, by connector; any other size is typed. Duplicates are refused.
Graphics
Both rows are properties of the virtio-gpu-av-pci device lines, so both restart. The adapter table lists every host Vulkan device with its vendor and device IDs, VRAM and driver; software rasterizers such as llvmpipe are left out unless they are the only device. Its Display row is host-gpu on the display device: auto, shown as Display (auto) on the first device, until a row is picked, then that GPU's Vulkan UUID, which survives reboots and driver updates where enumeration order does not. Picking Display on another row moves the display there and makes the old one render only; the display row offers no other role, because there is always exactly one. Each Render only row adds one display=off device bound to that GPU, up to eight. Host window is hostmem: the CPU reads GPU results from it cached instead of uncached, host memory backs it only as chunks are placed, and what does not fit falls back to guest RAM. At 256 MiB applications run out, so the list starts at 2 GiB.
Scrolling
Shown in full here. In the window the list scrolls and the amber bar stays pinned to the bottom.

A launch that fails
From the launcher, with the manager's own window closed, there is nowhere for a notice to go, so a failed launch is this same window in its failed state: whether the guest had to be started for it or was already up. The reason is a red callout in the words that came back, and the buttons are the log, Close, and Try again. Launched from the grid, the failure is a notice on the overview instead.
When it appears
Only when the guest is not already up. Launching into a running guest opens the application's window directly, with no splash at all.
Named phases
Machine, Windows, agent, application. A cold start is around 40 seconds and the slow part moves around, so a single spinner would tell you nothing about whether it is stuck.
Hide, not cancel
Hide sends it to the tray and the application still opens when it is ready. Cancel stops the launch and, if the manager started the guest for this, offers to stop it again.
No graphics phase
Every process opens the guest's one adapter through Windows' own loaders, so there is nothing to claim or wait for between the agent answering and the application running. A guest whose adapter is broken still boots; the Graphics page and the overview say why.

Two kinds behind one button
The add button in the applications panel opens a menu: Add a regular app is the configure dialog with an empty path, as before; Add a store app is this list. Each item's tooltip says what it is for, because "regular" means nothing until you have met the other kind.
What is listed
The packaged applications in the guest user's All apps list (the shell's AppsFolder), by name, sorted, each with the package family under it in mono so two of a name can be told apart. The agent answers it from the user's own session (list_store_apps), since packages are installed per user and the service sees none. Icons come with the list, drawn by Windows at the row's size, so the list arrives whole in one round trip.
Search
The field has the focus when the dialog opens, and narrows the list as you type, by name or package family, ignoring case. The footer counts what is shown against what there is. Enter adds the selected row; a double-click adds the one clicked.
What Add makes
An application entry like any other, named and iconed as Windows shows it, its icon read again at 256 pixels for the launcher. Its Configure dialog shows the store application's ID where a path would be (see Configure application). Adding one already in the grid selects that entry instead of making a second.
Starting one
Windows starts a store application by activation (launch_store_app), not from its executable. The process comes from Windows' broker, in no job of the agent's, so the mirror follows it by the process Windows names, and everything that process starts.
Open and opening
A tile carries a mark on its icon's corner instead of a line of text under its name: a hollow amber ring while the application is being opened, a solid green dot while its windows are mirrored here, nothing otherwise. The tooltip says which in words. A failed launch still says why under the grid.

Needs one new command
The agent has list_apps, launch and get_icon, but nothing that lists a directory. This adds list_dir: a path in, one page of entries out, each with name, whether it is a folder, size, modified time and an icon id. Paging matters because C:\\Windows\\System32 is five thousand entries and the reply slot is not the place to find that out.
Icons come from the same place as the app list
get_icon already extracts one from an executable or a shortcut. The picker asks for them lazily, only for the rows on screen, so opening a folder is one round trip and not one per file.
Opens where applications are
Default location is the Start menu Programs folder, which is exactly what the catalog already enumerates. Program Files and the mapped host drives are one click away in the sidebar.
Shortcuts are resolved
Choosing a .lnk stores what it points at, plus its arguments and working folder, so the entry keeps working if the shortcut is deleted later.
Not the SMB share
The share in Settings exists for your file manager and can be turned off. The picker goes over the agent connection, so it works regardless, and it sees the guest as the account that will run the program.

    Run Windows applications on Linux

    LSW installs a Windows guest and renders its windows onto your desktop. Four stages, roughly 25 minutes, mostly unattended.

    01 · IMAGE
    Point at a Windows ISO you have. Tools to download one or shrink one sit next to the field.
    02 · MACHINE
    Size cores, memory and disk, and name the local Windows account.
    03 · PAYLOAD
    Answer file, guest binaries, and the drivers that must exist on the first boot, the avgpu package among them.
    04 · INSTALL
    Unattended Windows setup, then the guest agent and the avgpu display driver.

    Nothing on this machine is modified outside ~/.local/share/lsw. The guest is a single qcow2 file you can delete.

          Why a tool
          The download page could only ever run once, in one place, and a wizard that had already committed to downloading could not go back. As a tool it can run before the wizard, be cancelled without losing anything, and be reopened to fetch a second edition.

                  The one rule

                  • Amber marks the guest. The Windows side of the machine, the primary action, the current wizard step, the focus ring. Nothing else.
                  • Green, blue and red carry state, never emphasis. A green button would be a bug.
                  • Every border is 1 px of line. Depth comes from fill, not from shadow, because Qt stylesheets have no shadow.

                  Rules

                  • If the machine produced it, it is mono. Paths, hex, ports, byte counts, durations, status words.
                  • Tabular numerals wherever digits stack: gauges, log timestamps, the setup table.
                  • Uppercase mono labels replace group box titles, which is how a panel gets a name without a heavy border and a floating caption.
                  • Both faces ship in the binary as Qt resources, so the UI looks the same on a host with no fonts installed.

                  Design system

                  Qt mapping

                  Nothing in this design needs a custom paint event. Every visual is reachable from a Qt stylesheet plus a handful of layout changes.

                  Straight stylesheet

                  • Buttons, inputs, combos, tables, scrollbars. Flat fills, 1 px borders, radii, one inset top highlight via border-top.
                  • Progress bars. ::chunk with a flat fill; the indeterminate stripe is a qlineargradient.
                  • Badges and pills. QLabel with an object name, exactly as the panel already does today.
                  • Panels. QGroupBox loses its title and gains a header QLabel, so the caption sits inside the border instead of on it.

                  Needs a small code change

                  • Wizard step rail. QWizard::setSideWidget() with a QListWidget, plus a slot on currentIdChanged.
                  • Two wizard pages become dialogs. DebloatPage and DownloadPage lose their page ids (Wizard::Debloat, Wizard::Download) and their widgets move into TrimImageDialog and DownloadImageDialog. Each owns its worker, each returns the path it wrote.
                  • Output directory. DebloatStager::trim() already takes an output directory, so the dialog passes the chosen folder plus a filename instead of settings().isos_dir(). The downloader gains the same pair.
                  • IsoChoicePage shrinks to one path field and two buttons. MicrosoftClient and IsoSourceFetcher move with the download dialog, so the page no longer owns network state or a ban flag.
                  • Manager nav rail. A QListWidget beside a QStackedWidget replaces the header button row. MainWindow keeps its tray; VmDetailPanel becomes the Overview page of the stack.
                  • Console and log move into the stack. ConsoleWindow and LogViewer become plain QWidgets that the stack owns; the pop out button reparents one into a QDialog.
                  • Settings page. New SettingsPage over a PendingChanges object: live keys write straight to Settings, restart keys stage until Apply, which calls Lifecycle::shutdown, rewrites the domain XML from the template, and starts it again.
                  • File manager bookmarks. DolphinPlaces gains an uninstall and a folder argument, and a sibling writes ~/.config/gtk-3.0/bookmarks for GNOME Files and Thunar. Both are toggles over the same SMB URL.
                  • Host folder into the guest. A <filesystem type='mount' accessmode='passthrough'> virtiofs device in domain.xml, plus the drive letter mapping in the guest. Restart only, hence the tag.
                  • Desktop entries. DesktopLauncher gains the category name as a parameter, a per-application publish flag on AppConfig, MIME registration, and a rewrite-all entry point for the button.
                  • Resolution. Live: a qom-set of the device's modes property (WxH between commas, first preferred; empty means the host monitors' modes), sent through libvirt's monitor passthrough, exactly what accel-virt's vm_resolution.py does over QMP. Also written on the device line so a boot starts at it. The scale is live too: the agent sets each display's DPI step in the user's session, where Settings sets it.
                  • Graphics settings. Three keys that become properties on the -device virtio-gpu-av-pci line in domain.xml's <qemu:commandline>: host-gpu, hostmem, plus one display=off device per other GPU. The <video> VGA goes (-vga none, or another adapter takes the desktop), guest RAM becomes a shared memfd, and an isa-debugcon on port 0x402 writes avgpu.log.
                  • Graphics page. Host facts from Vulkan enumeration and an API probe (Vulkan, EGL, OpenCL ICD, DXVK and vkd3d-proton in AV_D3D_PATH); device facts from the settings it booted with and qom-get modes; guest driver state from one new agent query; and a tail of avgpu.log.
                  • Host folders. A list of <filesystem> devices in domain.xml rather than one, each with a tag the guest maps to a drive letter.
                  • Launch splash. A frameless QDialog the manager shows when --launch <app-id> arrives and the domain is not running. Phases come from signals that already exist on Lifecycle and Monitor.
                  • Remote file picker. A new agent command list_dir (path, cursor, filter in; name, is_dir, size, mtime, icon id out, paged), and a RemoteFileDialog on the host: a QListWidget of places beside a QTreeView over a small model that fetches a page at a time and asks get_icon only for visible rows. Shortcut resolution happens agent side, so the host stores the target rather than the .lnk.
                  • Manager status bar. A QStatusBar fed from Lifecycle and AgentRpcClient.
                  • Empty state. A second page in a QStackedWidget inside the panel.
                  • Payload checklist. The existing payload page becomes a small QTableWidget, same shape as the setup table.
                  • Option cards. QRadioButton with the description as a child label, wrapped in a clickable QFrame.

                  Not doing

                  • No shadows, blur or transparency inside the app windows. Qt stylesheets cannot draw them, and faking them costs a paint event.
                  • No animation beyond what QProgressBar already does.
                  • No light theme for the app. The manager is a machine console and commits to one world. Tokens are named so a light set can be added later without touching layout.
                  • No icon font. Symbols are either real app icons from the guest or plain text.
                  • Trim is never mandatory. The pipeline keeps its own trim path for the unattended CLI runner, but the wizard never blocks on it.
